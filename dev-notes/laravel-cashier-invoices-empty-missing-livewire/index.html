Laravel Cashier invoices() Empty or Missing Invoices? A Checklist for Livewire Billing Pages

You're building the "Billing" page of a Laravel app. Stripe's dashboard shows the customer's invoices, but $user->invoices() comes back empty, or the unpaid invoice the customer is asking about isn't in the list. Or the list loads in a controller and then throws an error the moment you move it into a Livewire component. This checklist goes through the causes in the order that's quickest to rule out, then ends with a small component that maps Cashier invoices into rows a Livewire table can hold.

It's written against Laravel Cashier (Stripe) v16.9.0 and Livewire 3 and 4. Where older Cashier versions behave differently, that's noted.

Quick reference

What you see Most likely cause Check
Empty collection, no error The model has no Stripe customer id, or it's the wrong model 1
Open, draft or failed-payment invoices missing invoices() only returns paid invoices 2
Only recent invoices, or fewer than expected The default limit of 24, applied before the paid filter 3
"Property type not supported in Livewire for property" Cashier Invoice objects in a public property 4
Amounts 100× too big, or text where you expected a number Raw minor units vs formatted strings 5
Badge says "open" or "uncollectible", or there's no "overdue" Stripe statuses aren't portal statuses 6
Customer paid, list still says unpaid Stale data 7
Download returns 403 or 404 The invoice belongs to another customer, or the id is wrong 8

☐ 1. The model actually has a Stripe customer id

In Cashier v16 (and v14 and v15), invoices() starts with this check:

if (! $this->hasStripeId()) {
    return new Collection();
}

So a user without stripe_id gets an empty collection. There's no exception and nothing in the log. Check two things:

  • The column is filled for the user you're testing with. A customer created in the Stripe dashboard isn't linked to your user until you store its id, for example with createAsStripeCustomer() or createOrGetStripeCustomer().
  • You're calling it on the Billable model. If the Billable trait is on a Team or Membership model, auth()->user()->invoices() is the wrong object. One of the oldest questions about this, Laravel/Cashier invoices() returns empty Object, had the Cashier columns on a separate membership table.

Also make sure your app's Stripe keys are for the same mode (test or live) as the invoices you're looking at in the dashboard.

☐ 2. invoices() only returns paid invoices

This is the most common surprise. Cashier fetches the customer's invoices from Stripe and then keeps only the paid ones unless you ask for more:

foreach ($stripeInvoices->data as $invoice) {
    $invoiceInstance = new Invoice($this, $invoice);

    if ($invoiceInstance->isPaid() || $includePending) {
        $invoices[] = $invoiceInstance;
    }
}

That simplified excerpt is from v16.9.0, where isPaid() means status === 'paid'. So an invoice that is open (awaiting payment or after a failed charge), draft, uncollectible or void is dropped. For a customer billing page you almost always want all of them:

$invoices = $user->invoicesIncludingPending();
// same as $user->invoices(true)

Note: Cashier v14 and v15 checked Stripe's paid field instead of status ($invoice->paid || $includePending), with the Stripe API version pinned by Cashier (2022-11-15 in v14.14.0, 2023-10-16 in v15.8.0). Stripe removed Invoice.paid in API version 2025-03-31.basil, and Cashier v16 uses the current API version. If you copy filtering code from an older answer that reads $invoice->paid, check it against your Cashier and Stripe API versions.

☐ 3. The default limit is 24, and it's applied before the paid filter

Cashier sends limit: 24 to Stripe unless you pass your own. With the default invoices(), the paid filter runs on those 24, so a customer with many failed or open invoices can see fewer than 24 rows even when they have older paid invoices.

Pass Stripe list parameters as the second argument:

// up to 100, which is Stripe's maximum page size
$invoices = $user->invoices(true, ['limit' => 100]);

// only open invoices, filtered by Stripe
$open = $user->invoices(true, ['status' => 'open']);

For a long history, cursorPaginateInvoices($perPage) returns a Laravel cursor paginator over the same data (it always includes pending invoices).

If you need invoices for all customers (an admin revenue report, as in Laravel cashier list all invoices and total), looping over users and calling invoices() is one API call per user. That's a different job: list invoices from Stripe directly or store them locally from webhooks.

☐ 4. Don't put Cashier Invoice objects in a Livewire public property

This one only appears when the code moves into Livewire:

public $invoices;

public function mount()
{
    $this->invoices = auth()->user()->invoicesIncludingPending(); // breaks
}

Livewire sends every public property to the browser and back on each request, so it supports a fixed set of types: arrays, strings, integers, floats, booleans and null, plus BackedEnum, Collection, Eloquent collections and models, DateTime, Carbon and Stringable. Anything else needs a Wireable implementation or a custom Synthesizer. The 3.x and 4.x docs list the same types.

Laravel\Cashier\Invoice is none of those. Wrapping it in a Collection doesn't help, because Livewire's Collection support dehydrates each item, and each item is still an Invoice. The error you get is "Property type not supported in Livewire for property: [...]". The bracket may hold a large JSON dump, because the Invoice serialises to the full Stripe invoice.

You have three ways out:

  • A computed property (#[Computed]). It's evaluated on the server for each request and is not stored in the component state. This is the simplest option, and it's the one used in the example below.
  • Pass the data to the view from render(), which also stays on the server.
  • Store plain arrays, not objects, if you really need a public property. Pick the fields you show. Don't use $invoice->toArray(): in Cashier it returns the whole Stripe invoice (customer email, address, line items and more), which would all end up in the page.

☐ 5. Pick one money unit and stick to it

Cashier gives you two kinds of amount methods on an invoice:

Method Returns Example for $12.50
total(), amountDue(), subtotal() Formatted string, using the invoice's currency and cashier.currency_locale "$12.50"
rawTotal(), rawAmountDue() Integer in the currency's smallest unit 1250

Typical bugs are showing rawTotal() as dollars (100× too big), formatting an already formatted string, or summing strings. A safe rule is to keep the integer for sorting and sums and format it once, at display time.

For two-decimal currencies like USD or EUR, the smallest unit is a cent. Stripe also has zero-decimal currencies (JPY is one), where the integer is the amount, so don't hard-code / 100 for every currency. See Stripe's zero-decimal currency list. Cashier's own formatter already handles this, so total() is the safest string for display.

total() and rawTotal() add the invoice's starting_balance to Stripe's total. A customer credit is stored as a negative balance, so a credit lowers the figure. rawRealTotal() (formatted: realTotal()) is Stripe's total field as is. Pick the one that matches what the customer should see, and use it everywhere on the page.

☐ 6. Map Stripe's statuses to the ones your page shows

A Stripe invoice is always one of five statuses: draft, open, paid, uncollectible or void. There's no "overdue" and no "sent". Cashier has a helper for each one: isDraft(), isOpen(), isPaid(), isUncollectible() and isVoid().

Most portals show something friendlier. One mapping that's easy to explain:

Stripe status Shown to the customer as Notes
draft Hidden, or "Draft" Not finalised yet; number can still be null
open with a due date in the past "Overdue" Your own rule, not a Stripe status
open "Due" / "Unpaid" Includes invoices whose automatic charge failed
paid "Paid"
uncollectible "Unpaid" or "Contact us" Stripe can still move it to paid later
void "Void", or hidden

The due date catch: Stripe sets due_date only for invoices sent for manual payment (collection_method=send_invoice). For automatically charged invoices, the usual case with Cashier subscriptions, due_date is null, so dueDate() returns null and an "overdue" rule based on it never fires. For those, an open status already means the charge hasn't succeeded yet.

For automatically collected invoices, Stripe also waits about an hour after your webhook endpoints successfully respond to invoice.created before attempting payment, so you may not want to show a fresh open invoice as "unpaid" straight away.

☐ 7. The list is stale after the customer pays

invoices() asks Stripe each time it runs, so a page reload shows the new status. The problem is a Livewire component that fetched once in mount() and kept the result in state, or a local invoices table you never update.

  • With a computed property, the next request re-runs it. Add a refresh button that calls an empty action, or unset($this->invoices) to clear the cached value within a request.
  • If you store invoices locally, update them from Stripe's webhooks (invoice.paid, invoice.payment_failed, invoice.voided, invoice.marked_uncollectible). Cashier fires a WebhookReceived event for every webhook it receives, which you can listen to.

☐ 8. Downloads: always look the invoice up through the signed-in user

Cashier's PDF download is a single call. It needs the Dompdf library installed (composer require dompdf/dompdf):

use Illuminate\Http\Request;

Route::get('/billing/invoices/{invoiceId}', function (Request $request, string $invoiceId) {
    return $request->user()->downloadInvoice($invoiceId);
})->middleware('auth');

In v16.9.0, Cashier's Invoice constructor compares the model's stripe_id with the invoice's customer and throws InvalidInvoice if they differ. findInvoiceOrFail() and downloadInvoice() turn that into a 403, and an id Stripe can't find into a 404. Note that findInvoice() throws for another customer's invoice rather than returning null.

That check protects you only if you call it on the right model. Call it on $request->user() (or the team the user is authorised for), never on a user or team id taken from the URL or a Livewire property. In a Livewire action that receives an invoice id, call it on auth()->user() the same way.

Putting it together: a minimal Livewire component

This component lists every invoice for the signed-in user. It keeps the data out of the component state and turns each Cashier Invoice into a plain array:

<?php

namespace App\Livewire;

use Livewire\Attributes\Computed;
use Livewire\Component;

class BillingInvoices extends Component
{
    #[Computed]
    public function invoices(): array
    {
        return auth()->user()
            ->invoicesIncludingPending(['limit' => 100])
            ->map(fn ($invoice) => [
                'id' => $invoice->id,
                'number' => $invoice->number ?? '—',
                'issued_at' => $invoice->date()->toDateString(),
                'due_at' => $invoice->dueDate()?->toDateString(),
                'total' => $invoice->total(),         // formatted for display
                'total_minor' => $invoice->rawTotal(), // integer, for sums and sorting
                'status' => $this->label($invoice),
            ])
            ->all();
    }

    private function label($invoice): string
    {
        return match (true) {
            $invoice->isPaid() => 'paid',
            $invoice->isVoid() => 'void',
            $invoice->isDraft() => 'draft',
            $invoice->isUncollectible() => 'unpaid',
            $invoice->dueDate()?->isPast() => 'overdue',
            default => 'due',
        };
    }

    public function render()
    {
        return view('livewire.billing-invoices');
    }
}

In the Blade view, read it as $this->invoices and give each row a wire:key="invoice-{{ $row['id'] }}". The download link points at the route from check 8. If you add a search box or status filter on top of this list and it doesn't react, see Livewire search or filter not updating the table.

Note: this is an example to adapt, not a drop-in file. It assumes Billable is on your User model and that one page of up to 100 invoices is enough. Use cursorPaginateInvoices() beyond that.

If you don't want to build the table and badge yourself

Once you have the mapped array, what's left is UI. Billstack ($29) is a pack of Livewire components for billing portals.

Its CustomerInvoiceTable takes an array of rows much like the one above (id, number, issued_at, due_at, total, status and an optional currency) and adds a live search box and status filter. Its PaymentStatusBadge covers draft, sent, paid, overdue and void.

It does not connect to Stripe or Cashier, so you still do the fetching and mapping from this page. Three adjustments for its row shape:

  • Status: map open to sent or overdue, and pick one of its five statuses for uncollectible. Values it doesn't recognise are shown as Draft.
  • Total: pass a number in major units (12.50, not 1250 and not "$12.50").
  • Due date: a missing due date displays as a dash.

It requires PHP ^8.2, Livewire 3 or 4 and Laravel 10+, and it isn't affiliated with Laravel or Livewire.
